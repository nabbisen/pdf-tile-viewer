# Adding a Translation

Translations live in `crates/app/src/i18n/`.

## Steps

1. Add a new variant to `Locale` in `crates/app/src/i18n.rs`.
2. Add the language code to `Locale::from_tag` and to `supported_language` (system detection).
3. Create `crates/app/src/i18n/<lang>.rs` with a `message` function returning
   `Option<&'static str>` (returning `None` falls back to English).
4. Add a match arm in `t()` in `crates/app/src/i18n.rs`.
5. Run `cargo test -p app` — the completeness tests will check that every key
   can resolve without an empty string through fallback.

## How the language is chosen (RFC 043)

`ui.locale` (`"en"` / `"ja"`) wins. With `null`, `i18n::choose_locale(lang_env, os_locales)` — a pure
function, the only place with this logic — decides:

1. `LANG`, when set to a real locale (not empty, not `C` / `POSIX`), decides alone: Japanese for
   `ja…`, English for anything else.
2. Otherwise the first language in the operating system's preferred languages (read with the
   `sys-locale` crate on Windows, macOS and Linux) that the app has.
3. Otherwise English.

Tags may be BCP 47 (`ja-JP`) or POSIX (`ja_JP.UTF-8@euro`): they are lowercased and split on `-`, `_`,
`.` and `@`; the first part is the language. A new language needs a line in `supported_language` and
test cases next to the existing ones in `src/tests/i18n.rs`.

## Completeness policy (RFC 017 §9)

- The English catalog (`en.rs`) uses an exhaustive `match` — it is
  compiler-enforced complete. A new `MessageKey` cannot ship without an
  English string.
- Other catalogs return `Option`; gaps fall back to English and are
  acceptable during early translation work.
- Add the completeness test for your locale once it is fully translated.
