# Handoff — Release candidate 2.0.2, section B support: workflow dry run and Linux screen-reader log

Part of `rfcs/handoffs/release-2.0.2/release-candidate.md` (owner-authorized 2026-10-27). Section A is done. Working model: one actor at a time; nothing is committed to `main` by this handoff. **GUI rules apply** for Task 2 — `.git-exclude/rules/project-instructions-gui-common.md`.

## Hard rules (DEC-001)
- **Never** push a tag, run a workflow, create a release or open a PR on `origin` (`nabbisen/pdf-tile-viewer`). Everything in Task 1 happens in a **separate throw-away repository** (see below). Before **every** `git push` or `gh` write command, run `git remote -v` / read the target and confirm it is the dry-run repository, not `origin`; use an explicit URL or remote name in the command.
- No *Prepare release* and no tag on the real repository. The real 2.0.2 release is the owner's decision after the architect's readiness report.
- Work in a throw-away `git clone` (never a worktree: tags are shared between worktrees; a tag was once lost that way). Never run `git tag -d` against anything but tags you created for the dry run.
- Do not touch the owner's real `~/.config/pdf-tile-viewer`; use isolated XDG directories.

## Task 1 — workflow dry run (RFC 036; instructions: `.git-exclude/review-request/036-supply-chain/README.md` § 9, and `docs/src/contributors/dev.md` § *Trying workflow changes on a fork*)
GitHub does not allow forking your own repository into the same account, so use a **new public repository** `nabbisen/pdf-tile-viewer-rc-dryrun` (public: free Actions minutes, and the source is public anyway). Create it with `gh repo create nabbisen/pdf-tile-viewer-rc-dryrun --public` (no clone, no template), add it as the remote `dryrun` in a throw-away clone of `main` at the current head, and push **only `main`** (`git push dryrun main`; no tags). In that repository's settings: Actions enabled; turn Dependabot off (it would open PRs). The `gh` token has no `delete_repo` scope: **leave the deletion to the owner** and say so in the report.

Run on the dry-run repository, in this order, recording run URLs and results:
1. **CI** on the pushed `main` head must be green (all jobs, including clippy, cargo deny, the three OS builds).
2. **Prepare release negatives** (§ 9 B): dispatch with a version that has no `unreleased` CHANGELOG heading → must fail with "must contain the heading"; (the "red CI" negative only if cheap).
3. **Prepare release, positive:** in the dry-run clone add `## [2.0.2-rc.1] - unreleased` to `CHANGELOG.md` above the 2.0.2 section (any text), push to `dryrun main`, wait for CI, dispatch *Prepare release* with `2.0.2-rc.1`. Expect: one commit "Prepare release 2.0.2-rc.1" by `github-actions[bot]` touching exactly `CHANGELOG.md`, `Cargo.lock`, `Cargo.toml`, `packaging/windows/AppxManifest.xml` (`Version="2.0.2.0"`); CI runs on it; **no tag exists** (`git ls-remote --tags dryrun`).
4. **Tag on the dry-run repository only:** `git tag -a 2.0.2-rc.1 <printed commit> -m 2.0.2-rc.1 && git push dryrun 2.0.2-rc.1`. Expect § 9 A: `verify-tag` passes; four build jobs and the source archive succeed; "Verify release assets" passes; a GitHub **pre-release** with exactly five files (`pdf-tile-viewer-v2.0.2-rc.1-{linux-x64,macos-arm64,macos-x64}.tar.gz`, `…-windows-x64.zip`, `pdf-tile-viewer-v2.0.2-rc.1.tar.gz`); the release notes equal the CHANGELOG text of that section plus the footer; `msix-store.yml` produces `pdf-tile-viewer-2.0.2.0.msix`.
5. **Inspect the downloaded assets** (each into its own new empty directory; treat as untrusted; no archive member is executed except the Linux binary in step 6): every archive extracts flat (`bin/`, `resources/`); `notes.txt` `Bundled PDFium library SHA-256` equals the library hash from `ci/pdfium-checksums.txt`; the Linux archive's SHA-256 recorded. Run the extracted Linux package once (isolated XDG dirs, X11, one instance, stderr empty) to prove the CI-built binary starts.
6. **Guards** (§ 9 C, in this order, one run each): (1) tag `2.0.3` on the same commit → `verify-tag` fails ("does not equal the workspace version") and nothing else starts; (2) a tag on a commit only on a side branch → "not an ancestor"; (3)–(5) only if the earlier steps were clean and CI minutes allow: stray file in `release-files` → `UNEXPECTED …`; wrong hash in `ci/pdfium-checksums.txt` → `MISMATCH`; a clippy warning → clippy job fails. Delete the guard tags/branches you create on the dry-run repository afterwards (never on `origin`).
7. Stop at the **first anomaly** that is not an expected failure; report it, do not work around it. Do not repeat a failed set a second time without asking the architect.

## Task 2 — Linux screen-reader log (a record of what is spoken; not a verdict)
Purpose: give the owner and architect the text Orca speaks for the RC build, before the owner's listening session (`rfcs/handoffs/037-user-facing-error-presentation-and-accessible-names/screen-reader-listening-session.md`). Use the **CI-built Linux package from Task 1 step 4** if it exists, otherwise a local release build of the head. Method: the one of WP0 C7 (`.git-exclude/review-request/wp0-evidence-run/README.md` § C7 and its `c7-*.txt` files): app and Orca as transient `systemd --user` units, Orca's data directory in a scratch directory (never the owner's `~/.local/share/orca`), debug log captured, `screen-reader-enabled` restored to its prior value afterwards. On Wayland Orca cannot inject its navigation keys: use focus-driven speech (Tab, AT-SPI actions) and the X11 backend for the one step that needs a pointer (opening the zoom view); state the backend per line.
Cover scenarios **1–7 and 10–14** of the listening-session table (skip 8–9, which need pointer-driven reading). For each: the exact lines Orca spoke, in order, and one of **Spoken / Silent / Spoken twice / Wrong text** (objective only — do not rate quality). Compare against WP0 C7 where the same step existed (WP0: search entry and jump entry silent on focus; the open-failure alert not announced) and say what changed. Do the Japanese run (`ui.locale` = `ja` in the scratch `settings.json`) for scenarios 1, 3, 5 and 14 and note the voice/language Orca reports if the log shows it.
Rules: one app instance and one Orca at a time; focus verified before every synthetic input (`niri msg -j focused-window`; on X11 compare the window id); no frame sampling; at most ≈ 30 minutes of Orca running; abort at the first anomaly.
